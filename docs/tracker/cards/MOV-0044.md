## Why this exists

A chosen AI can read private move photos but cannot file a new one through the
canonical OAuth toolset. The app/API and legacy tools prove foundations, not a
canonical end-to-end workflow.

## Current truth

`get_evidence_media` is the bounded read. Existing upload start/finalize lives
outside canonical MCP; legacy `add_images`/`attach_photos` are compatibility
paths. MOV-0040 already names canonical `save_evidence_media` as the gap.

## Next safe action

After MOV-0043, add `save_evidence_media` actions `begin_upload`,
`finish_upload`, and `attach` around direct HTTP PUT. File committed media IDs
only onto authorized Moving targets. Route legacy adapters through the same
control plane and record the media gap as resolved in MOV-0040 without claiming
its broader convergence complete.

## Definition of done

- [ ] Normal connected-AI transfer is begin → direct PUT → finish.
- [ ] Attach is a domain workflow action for a real Moving target, not raw CRUD.
- [ ] Bounded `get_evidence_media` behavior and named omissions are preserved.
- [ ] Provider URLs/keys never cross the MCP read response.
- [ ] Stable invalid-image, upload-incomplete, unavailable, unauthorized,
      operation-conflict, and session-expired failures are documented/tested.
- [ ] Legacy adapters cannot bypass canonical validation or authority.

## Constraints

Do not remove a live tool or door, absorb MOV-0040's unrelated convergence,
accept remote URLs, or use MCP base64 for normal uploads. Preserve the shipped
read ceilings and omission semantics.

## Completion evidence

Not started. Canonical OAuth MCP still has no media-write tool.
